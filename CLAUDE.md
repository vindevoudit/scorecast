Full-stack football prediction web app. React 18 + Vite frontend, Node/Express backend, PostgreSQL via Sequelize. Users make picks on games, join groups, send friend requests, comment + react on games, earn badges, and compete on probability-weighted leaderboards. ## Tech stack at a glance

- **Sports (Tier 34)**: football + T20 cricket. `leagues.sport` is the taxonomy, denormalised onto `games.sport`, which [lib/scoring.js](lib/scoring.js) dispatches on. Football keeps the odds-weighted 3-way market; cricket is a flat +50 winner plus two optional runs legs worth up to +100 each. Fixtures for cricket are imported from a committed schedule file ([data/cpl-2026-fixtures.json](data/cpl-2026-fixtures.json)) and results are entered by hand — there is no cricket feed
- **Frontend**: React 18 + Vite + Tailwind CSS
- **Backend**: Node 18+ / Express 4
- **DB**: PostgreSQL via Sequelize 6; migrations via sequelize-cli + umzug
- **Auth**: HttpOnly cookies — 15-min access JWT + 30-day rotating refresh (bcryptjs for passwords). ~~Opt-in TOTP 2FA via `speakeasy` + `qrcode` with bcrypt-hashed recovery codes.~~ 2FA was parked in Tier 22 for the marketing launch — see Critical considerations + routes/auth.js header for the revival recipe.
- **CSRF**: double-submit cookie (`sc_csrf` cookie + `X-CSRF-Token` header) on state-changing routes
- **CORS**: env allowlist via `CORS_ORIGINS`; throws on boot in production if unset. Non-prod fallback is a localhost-only allowlist (Tier 22 M2 — was previously `true`).
- **Security headers**: helmet (CSP, HSTS with `preload`, X-Frame-Options: DENY, etc.) + extended Permissions-Policy (camera/mic/geo/payment/USB/fullscreen/motion-sensors/interest-cohort all denied) (Tier 22 M3 + L4)
- **Email**: pluggable transport via [lib/email.js](lib/email.js) — Resend when `RESEND_API_KEY` set; log-only fallback otherwise. Used by verify-email + password-reset flows.
- **Validation**: zod on every POST/PUT body
- **Rate limiting**: express-rate-limit on login, register, client-errors, comments, friend-requests, picks, forgot-password, group password-join, /me/{password,email} (`sensitiveAccountLimiter`, 10/hr/IP — Tier 22 H1), /me/{push-preferences,onboarding-completed,accept-terms} + PUT /me + /notifications/{:id/read,read-all} (`lightWriteLimiter`, 60/min/IP — Tier 22 H1), group invite (`inviteLimiter`, 5/min/IP — Tier 22 H2)
- **Logging**: pino + pino-http with request-id correlation
- **Error reporting**: React `ErrorBoundary` + window listeners → `POST /api/client-errors` → structured log; Sentry opt-in via `SENTRY_DSN` / `VITE_SENTRY_DSN`
- **HTTP**: gzip via `compression` middleware
- **Leaderboard cache**: in-memory `Map` with 30s TTL atop materialized `user_scores` + `user_scores_overall` tables (Tier 24 — incremental dual-writer on every score-affecting mutation; reads are sub-ms indexed SELECTs regardless of user count)
- **State (Tier 13.6/13.7)**: React Context — `AuthContext` (user + auth flow), `DataContext` (games/picks/groups/leaderboard/friends/profile + mutations), `NotificationContext` (toast banner). Selector hooks `useGames`/`usePicks`/`useGroups`/`useLeaderboard`/`useFriends` + `useRequest` (CSRF + 401 refresh-retry). App.jsx is a layout shell consuming hooks
- **Server layering (Tier 13.1–13.5)**: `routes/*.js` (parse + auth + service call) mounted at `/api`, `services/*.js` (domain logic: Pick / Game / Group / User / Comment / Leaderboard / Notification / Badge), `lib/` (cross-cutting infra: scoring, users, groups, friends, auth cookies/tokens, errors, response, errorMiddleware, leaderboardCache, email). `server.js` is composition shell only (≤ 200 lines)
- **Lint + format (Tier 9.1)**: ESLint 9 flat config + Prettier 3 + `husky` v9 + `lint-staged`. Pre-commit runs `lint-staged`; pre-push runs `npm run build`
- **Code-splitting (Tier 9.2 + Tier 30)**: `React.lazy` + `<Suspense>` around AdminPanel, ProfileView, PicksHistory + the Phase 1 lazy-views (Settings / Friends / Groups / Leaderboard). Vite `manualChunks` splits `react`/`react-dom` (vendor), `@sentry/*` (sentry), `@radix-ui/*` (radix), `motion/*` (motion — Tier 30 Phase 2, ~30 KB gzip), and `html-to-image` (Tier 30 Phase 3 A4, ~3 KB gzip; the share flow dynamic-imports it on demand). Dependabot (`.github/dependabot.yml`) opens weekly PRs for npm / pip / github-actions / docker
- **E2E tests (Tier 5.5 + 5.5b + per-endpoint API suite)**: `@playwright/test` runs against `npm run build && node server.js` on port 3100 with `NODE_ENV=test`. Specs live in [tests/e2e/](tests/e2e/) (UI + flow specs) and [tests/e2e/api/](tests/e2e/api/) (per-route boundary specs — one file per `routes/*.js`, ~270 tests covering happy path + 401 + 403 + CSRF + 400 + 404 + ownership for all 68 endpoints). `globalSetup` syncs the schema, applies migrations, truncates + reseeds three deterministic users (`e2e_admin`, `e2e_alice`, `e2e_bob`) and three upcoming games per run. Shared helpers in [tests/e2e/helpers/](tests/e2e/helpers/): `auth.js` (UI register/login/logout), `selectors.js` (`closestCard`), `admin.js` (admin tab nav), `api.js` (HTTP helpers `apiLogin`/`apiAnon`/`stripCsrf`/`setGameResult`/`createPick`/`getLeaderboard` + DB helpers `resetUserLockout`/`insertPasswordResetToken`/`clearFriendships`/`clearPicksAndBadges`/`clearNotifications`/`clearGameResults`/`clearComments`/`clearGroupsCreatedBy`/`clearLeaguesByName`/`clearAuditLog`/`getUserId`/`deleteUserByUsername`/`clear2faForUser`/`setUserPassword`/`updateUserFields`), and `apiAssertions.js` (`assertOk`/`assertUnauthorized`/`assertForbiddenWithoutAdmin`/`assertCsrfRejected`/`assertValidationError`/`assertNotFound`/`assertNoContent`/`expectShape` — one-call helpers that collapse per-test boilerplate). Each spec resets only the state it touches via the DB helpers so order across the file doesn't matter; specs **must not** call `closeDb()` in `afterAll` because workers:1 shares the Sequelize pool across specs. Local: `npm run test:e2e` (needs `scorecast_test` DB — credentials are derived from `.env`'s `DATABASE_URL` by swapping the path). Rate limiters are skipped when `NODE_ENV=test` so the suite doesn't 429 itself. Full-suite runtime ~5 min
- **Cloud deploy (Tier 9.6–9.9)**: Azure Container Apps (Consumption, scale 0→3) + Azure DB for PostgreSQL Flexible Server (B1ms) + Azure Container Registry + Key Vault (RBAC mode) + Log Analytics + App Insights. IaC via Bicep in [infra/](infra/). Secrets resolved at app boot via system-assigned managed identity → Key Vault. **No Redis in prod yet** — Tier 10.4 will add managed Redis
- **CD (Tier 9.7)**: `.github/workflows/deploy.yml` on push to main — build image → push to ACR → `az containerapp job start scorecast-migrate` (one-shot migration) → `az containerapp update --image` (rolls new revision) → smoke `https://bantryx.com/healthz`. Auth via GitHub OIDC federated credential → Azure AD app `scorecast-github-cd` (no long-lived secrets)
- **Custom domain + TLS (Tier 9.8)**: `bantryx.com` apex on Cloudflare (DNS only, grey-cloud), `www.bantryx.com` → apex via Cloudflare 301 redirect rule. Free Azure managed cert (HTTP-01 ACME validation, auto-renews every 6 months)
- **External football data (Tier 4b + Tier 18)**: [football-data.org v4](https://www.football-data.org/) TIER_ONE plan (20 req/min, paid since 2026-05-23 — was free 10 req/min) via [lib/footballApi.js](lib/footballApi.js) — provider-agnostic surface (`getCompetitions` / `getFixtures` / `getLiveMatches` / `getMatchesByIds`). Daily fixture sync (cron `0 3 * * *` UTC) + 30-s live-score poll (Tier 18, was 60-s) managed by [lib/scheduler.js](lib/scheduler.js) (node-cron + `pg_try_advisory_lock(crc32(jobName))` for multi-replica safety). Live-score job uses a single global `?status=LIVE,IN_PLAY,PAUSED` call regardless of how many leagues are tracked, followed by a reconcile pass via `?ids=` for any local in-progress games that fell off the LIVE filter (caught the IN_PLAY → FINISHED transition window). Picks remain winner-only (multi-kind deferred). Cost: €19/mo
- **Probability models** (Tier 17 + intl-model 2026-05-28): per-league XGBoost `multi:softprob` boosters with native JSON dumps in [lib/ml/models/](lib/ml/models/). **PL**: [PL_elo.json](lib/ml/models/PL_elo.json) (615 trees, val mlogloss 0.944, K=20 flat, HFA=0). **INT (World Cup + future Euros/Copa)**: [INT_elo.json](lib/ml/models/INT_elo.json) (615 trees, val mlogloss 0.883, FIFA-style K-multiplier tiers — WC ×3.0, WC qualifiers + continental finals ×2.5, continental qualifiers + Nations League ×2.0, Confed Cup + Olympics ×1.5, friendlies ×1.0 — applied as both the Elo K-factor weight AND the XGBoost row sample_weight; trained on the martj42 international archive 1872-2026 = 49,215 matches × 333 teams). Both are 2-feature `(home_elo, away_elo)` boosters consumed by [services/PredictionService.js](services/PredictionService.js) `MODEL_PATHS[sourceLeagueId]`. For neutral-venue fixtures (default for WC, manually settable via `games.neutralVenue`) the cascade symmetrizes inference by averaging `predict(home, away)` + `predict(away, home)` swapped — guarantees `predict(A, B) === predict(B, A)` mirror invariant. Schema additions in the games table: `games.neutralVenue BOOLEAN DEFAULT FALSE`, `games.eloKMultiplier NUMERIC(4,2) NULL` (null = 1.0).
- **Audit log (Tier 4b)**: [middleware/auditLog.js](middleware/auditLog.js) `auditMutation(action, entityType)` wraps every mutating `/api/admin/*` endpoint; records via `res.on('finish')` so the final status code reflects the real outcome. Payloads truncated at 4KB. Read-only paginated view at `GET /api/admin/audit-log` + the AuditLog admin tab

## Running

```bash
# Local dev (two terminals, hot reload):
node server.js       # backend on :3000 (auto-migrates in dev)
npm run dev          # Vite frontend on :5173 (proxies /api → :3000)

# Build + prod-like single-process:
npm run build        # produce dist/
npm start            # build + node server.js

# Migrations:
npm run db:migrate   # apply pending migrations (CD runs this as a one-shot job)

# Lint/format:
npm run lint         # ESLint flat config
npm run format       # Prettier --write
npm run format:check # Prettier --check (used by CI)

# Containerized local stack (matches prod image; uses NODE_ENV=production
# inside the container, so login cookies are Secure → won't transmit over
# http://localhost. For full-app dev with hot reload, use the two-terminal
# flow above):
docker compose up --build
```

## Critical considerations (don't break these)

Every item below is a load-bearing invariant or gotcha that **isn't obvious from reading the code**. These are the things future-you will get burned by.

- **2FA is parked, not deleted (Tier 22 — commit `b2bd286`)**: the route handlers, frontend components, and zod schemas were removed; the `users.{totpSecret, totpEnabledAt, totpRecoveryCodes}` columns + every migration + the `lib/auth.js` `CHALLENGE_COOKIE`/`CHALLENGE_TTL_MS` constants + the `speakeasy`/`qrcode` npm deps are preserved by design. Revival: `git revert <commit-1-SHA>` restores everything end-to-end with zero schema work. **Before reviving**, audit `users.totpEnabledAt != null` — none should exist today (migration `20260514000001-disable-all-2fa.js` already cleared them all in May), but if any creep in, decide whether to enforce 2FA for those users immediately on the revival commit OR wipe the columns first. **The `twoFactorEnabled` field in GET /api/me stays in the response** as a no-op signal until revival — don't remove it. **The marker comment at the top of routes/auth.js + routes/me.js IS the revival recipe** — keep them intact.
- **Web Push endpoint allowlist (Tier 22 H4)**: [validation/schemas.js](validation/schemas.js) `pushSubscribeSchema.endpoint` refine() rejects any URL whose host isn't in `PUSH_ENDPOINT_HOSTS` (FCM / Apple / Mozilla) or matching `PUSH_ENDPOINT_HOST_SUFFIXES` (`.notify.windows.com`, `.push.apple.com`). Plus an HTTPS-only check. New push provider = schema bump in both places. [services/PushService.js](services/PushService.js) `sendToSubscription` carries a defensive private/loopback-IP block (127._, 10._, 172.16-31._, 192.168._, 169.254.\* incl. Azure IMDS, ::1, fc/fe80) that drops the subscription on send rather than risking an SSRF outbound — covers DNS-rebind + stale-row scenarios that bypass the schema gate at write time. **Don't bypass either layer** when adding push providers.
- **Group-comment edit/delete re-checks membership (Tier 22 H3 IDOR)**: [services/CommentService.js](services/CommentService.js) `edit()` and `remove()` call `assertStillMember(comment, userId)` for any comment with a `groupId`. Without this, a user who leaves a group can still PUT-rewrite (or DELETE) their old comments inside it, defeating the membership gate `create()` enforces. Admin override on `remove()` bypasses the membership check (admin scope outranks group membership); `edit()` has no admin override (admins shouldn't be impersonating other authors).
- **MAX_GROUP_MEMBERS cap (Tier 22 M4; raised to 2000 post-Tier-24)**: [services/GroupService.js](services/GroupService.js) caps every group at 2000 members (env-overridable via `MAX_GROUP_MEMBERS`, clamped to [10, 5000]). Enforced inside the 4 add-member paths: `joinPublic`, `joinWithPassword`, `acceptInvite`, `approveJoinRequest`. Originally 500 — the cap existed because the pre-Tier-24 per-group leaderboard rebuild walked every pick × every game × every member in JS (~O(picks × games × members)) and a 10k-member group blew out the cache payload. Tier 24 replaced that with a single indexed `UserScore` SELECT against a member-id `IN` clause inside [services/LeaderboardService.js](services/LeaderboardService.js) `getForGroup`, so rebuild is now O(N) and sub-100ms at 2000. Route output is sliced to `limit ≤ 50` before the wire, so payload stays bounded regardless of group size. Further raises above 2000 should still re-check the in-memory sort + cache payload size (≈200 bytes/row × N × filter-combo cache slots) on the live container's memory ceiling.
- **`pushPreferencesSchema` is partial-update friendly (Tier 22 drive-by)**: uses `z.record(z.string(), z.boolean())` + a refine() that gates keys against `PUSH_NOTIFICATION_TYPE_SET`. Zod 4's `z.record(z.enum([...]), z.boolean())` would require every enum key to be present (regression hit in Tier 22 verification), breaking the documented "only specified keys flip; rest persist" merge contract that `PushService.updatePreferences` JSONB merge depends on. **Don't switch back to the enum-keyed form** without fixing the merge semantics in PushService at the same time.
- **HSTS is on the preload list path (Tier 22 M3)**: helmet config sets `hsts: { maxAge: 63072000, includeSubDomains: true, preload: true }` (2 years). After 30 days of stable production traffic with this header, submit `bantryx.com` at https://hstspreload.org to hardcode HTTPS in every modern browser. Until then, every first-visit-on-new-device is still a one-shot MITM downgrade window — preload eliminates that.
- **`/healthz` body is `{ ok: true }` exactly (Tier 22 M1)**: no `uptime` field. Container restart timing leaks deploy patterns to attackers; Azure Container Apps metrics already carry this for legitimate operators. `tests/e2e/api/health.spec.js` asserts the absence of `uptime` so a future re-add fails CI. The DB-pinging probe is `/readyz` — keep them separate (per Tier 20 Chunk 7's invariant).
- **CORS non-prod fallback is localhost-only (Tier 22 M2)**: when `CORS_ORIGINS` is unset (only possible in dev/test — production throws at boot), the fallback allowlist is `['http://localhost:5173', 'http://localhost:3000', 'http://127.0.0.1:5173']`. Previously `true` (allow any origin) which would silently accept credentialed requests from any host if a future staging env forgot to set CORS_ORIGINS. A new staging environment MUST set CORS_ORIGINS explicitly.
- **npm `overrides.uuid` pinned to ^11.1.1 (Tier 22 H6)**: `uuid <11.1.1` has a moderate-severity buffer-bounds CVE reachable via sequelize. Direct dep is at ^11.1.1; the `overrides` block in package.json forces the same version on the sequelize transitive without requiring a semver-major sequelize bump. **Don't drop the overrides entry** until sequelize ships its own uuid bump and we audit the resulting dep tree.
- **Multi-sport (Tier 34) — `games.sport` is the market switch and it is DENORMALISED**: `leagues.sport` (`'football' | 'cricket'`) is the taxonomy; `games.sport` is copied from it at insert and is what [lib/scoring.js](lib/scoring.js) `scorePick` dispatches on. The denormalisation exists so `scorePick(pick, game)` stays a pure function of its two arguments — it is called from ~10 places (`UserScoreService.computePoints`, `PickService.listFriendsPicks`, `UserService`, `StatsService`, `lib/users.js`, `lib/groups.js`, the client mirror, two marketing renderers) and a league join would have to be threaded through every one. **There is NO FK-level enforcement**, so every writer must stamp it: `GameService.createGame` (resolves it from the owning league, never from the request body), `LeagueService.upsertFixture`, and [scripts/import-cricket-fixtures.mjs](scripts/import-cricket-fixtures.mjs). **A projection that forgets to select `sport` silently mis-scores every cricket pick** — the game arrives with `sport === undefined`, `scorePick` takes the football branch, and both runs legs vanish with no error. That exact bug was found and fixed in `StatsService`'s `attributes` list; check any new explicit projection. `leagues.sport` is deliberately NOT updatable (`updateLeagueSchema` omits it) — flipping it would orphan every existing game on the old market. [lib/sports.js](lib/sports.js) ↔ [src/utils/sports.js](src/utils/sports.js) are a mirrored pair, same rule as `lib/stages.js`.
- **T20 cricket scoring — flat winner + prorated runs (Tier 34)**: winner leg is a **flat +50** (deliberately NOT odds-weighted; cricket has no probability model and its games sit on the `0.5 / 0 / 0.5` sentinel forever). Each optional runs leg pays `max(0, 100 - |effective - predicted|)`, so a match tops out at **250** vs football's ~100. `effectiveRuns(game, side)` scales a short innings to a **20-over equivalent** — `runs × 120 / ballsFaced` — **unless the side was bowled out**, in which case the score stands (the `allOut` check runs BEFORE the ball count, since an all-out side has almost always faced fewer than 120 balls). **Balls are stored, not overs**: cricket overs are base-6, so `17.2` means 17 overs 2 balls and decimal arithmetic on it is wrong; `oversToBalls` rejects a `.6`–`.9` fraction rather than coercing it. **Both causes of a short innings prorate** — a chase finishing early as well as rain — so 130 off 80 balls counts as 195 and predicting the literal score of a successful chase pays 35, not 100. That is intended (it makes the market about run rate) and is locked by a test; the UI must state it before the user types. `homeAllOut`/`awayAllOut` is authoritative for scoring while `homeWickets`/`awayWickets` is display-only — they are separate because a side can be all out at 9 down with a batter absent hurt.
- **Cricket scorecard writes go ONLY through `POST /api/admin/games/:gameId/cricket-result` (Tier 34)**: [services/CricketResultService.js](services/CricketResultService.js) writes the innings columns in their own transaction and THEN calls the **unmodified** `GameService.setResult`, whose `SELECT ... FOR UPDATE` re-read observes them. **That ordering is load-bearing**: written the other way round, `applyPickTransition` would recompute the same points, hit its `oldResult === newResult && oldPoints === newPoints` short-circuit, and **silently drop the correction** while the UI's live `scorePick` showed the new number. Known accepted seam: the two transactions mean a crash between them leaves the scorecard written and points unapplied — recovery is re-submitting, which is idempotent. The scorecard columns are deliberately absent from `updateGameSchema`, so the game-edit form (which does `Object.assign` + `save` with no re-scoring) cannot reach them. `result: 'draw'` is rejected for cricket in both `cricketResultSchema` and `bulkSetResult` — `pick.choice` is only ever `home`/`away`, so a drawn cricket game would award no winner points while the runs legs still scored.
- **Sport-scoped leaderboards are a PARALLEL path (Tier 34)**: `GET /api/leaderboard?sport=` dispatches to [services/SportLeaderboardService.js](services/SportLeaderboardService.js); without the param the existing `LeaderboardService` path is untouched. The split exists because a sport filter resolves to `leagueId IN (...)`, and all three existing read sites collapse rows with `new Map(rows.map((r) => [r.userId, r.points]))` — one row per `(userId, leagueId, seasonId)`, so **any multi-row match means last-row-wins and the rest of a user's points are silently dropped**. That is a live latent bug for any league with two seasons (logged in TODO.md); the sport path sums in SQL instead. Cache keys piggyback on the existing contract: the group key is `group:<id>:sp:<sport>` **specifically so `invalidatePrefix('group:<id>')` still matches it** — a tidier-looking `sport:<sport>:group:<id>` would leave membership changes stale on the sport tabs only. Friends stay uncached (per-viewer keyspace). `SUM()` over an integer column returns bigint, which node-postgres hands back as a **string** — the explicit `Number()` is what stops ranking going lexicographic.
- **Football-only machinery is guarded by sport (Tier 34)**: the four football cron jobs (`syncFixtures`, `syncLiveScores`, `reconcileInProgressGames`, `postMatchdayGraphics`) filter `League.findAll({ where: { active: true, sport: 'football' } })`; `LeagueService.syncFixtures` throws for a non-football league (without it, an admin clicking Sync on CPL would send `'CPL'` to football-data.org as a competition code); `PredictionService.onResultUpdated` returns early for non-football. **`sendKickoffReminders` is deliberately NOT filtered** — cricket should get reminders. Note `leagues.active` does double duty: it gates those crons AND is what `routes/leagues.js` exposes publicly, so an inactive league is invisible in the league picker.
- **Scoring formula is duplicated in FIVE places, not two**: [lib/scoring.js](lib/scoring.js) (`scorePick`, authoritative — used by `lib/users.js` `buildUserSummary` and `lib/groups.js` `buildGroupLeaderboard` to compute leaderboard points) and [src/utils/scoring.js](src/utils/scoring.js) (client-side preview), plus three copies that also carry the formula and must move with them: [scripts/backfill-user-scores.mjs](scripts/backfill-user-scores.mjs) (inline over a raw SQL projection — **a re-run without the cricket branch would rescore every cricket pick with football math and wipe every runs point from `user_scores`**), [lib/jobs/postMatchdayGraphics.js](lib/jobs/postMatchdayGraphics.js) `pointsForWinner`/`pointsForDraw`, and `marketing/lib/livedata.mjs`. All five must stay in sync in the same commit. Two branches: `result === 'home' | 'away'` → `(1 - winning_probability) × 100`; `result === 'draw'` → `(P_d × opposite_team_prob / (P_h + P_a)) × 100` (partial credit per the draw-scoring tier).
- **Draw scoring — picks stay winner-only**: `pick.choice` is `'home' | 'away'` only; there is no "pick the draw" option. The `'draw'` result enum value just awards partial credit instead of zero. Strict `winRate` semantic preserved — picks where `choice === result` literally (so draws never count as wins regardless of partial-credit points awarded). Old `result=null + status='finished'` games stay frozen at 0 pts on purpose — the migration does NOT backfill historical draws to `'draw'` to avoid retroactively reshuffling the leaderboard. `expectedDrawPoints(side, game)` in `src/utils/scoring.js` returns `null` when `drawProbability ≤ 0`, which makes the `PayoutMatrix` Draw row show literal `+x` / `+y` placeholders for games where draw scoring isn't configured (instead of `+0`) — so until ML or admin writes a non-zero `drawProbability`, the row is visibly "pending" rather than misleadingly "zero". The `ScoreboardBody.winningSide` is narrowed to `home | away` so a `'draw'` result leaves both team boxes un-dimmed (no green ring on either side; the outcome badge / locked-pick chip carry the "Drew +N pts" framing). Notification text on a scored draw reads `Your pick on X vs Y: Drew +N pts` — no `✓` / `✗` symbol since neither is appropriate.
- **Design tokens, not color literals (Tier 11)**: every component must consume tokenized utilities (`bg-base`, `bg-elevated`, `text-fg`, `text-accent`, `border-default`, etc.) defined in [src/index.css](src/index.css) `:root` / `:root[data-theme='light']`. The theme system is binary (Light/Dark); `system` mode was removed in Chunk 3 — defaults to Dark (matches the brand). Legacy `'system'` values in `localStorage.sc_theme` normalize to `'dark'` on read.

- **Win-streak service (Tier 30 Phase 3 A1 Revision — 2026-05-31)**: [services/StreakService.js](services/StreakService.js) `applyForUser(userId)` is called fire-and-forget POST-transaction from `GameService.{setResult, bulkSetResult, applyLiveUpdate}` — the THREE result-scoring entry points. Pick creation no longer affects the streak; **don't reintroduce a hook from PickService.createPick**. Each scored pick classifies as W (`pick.choice === game.result` for `home`/`away` result), D (`game.result === 'draw'`), or L (any other scored result). Streak rule: W → `current += 1`, D → no-op, L → `current = 0`. The pure `computeStreakFromPicks(scoredPicks)` recomputes the whole streak from history on every event — sort key `(game.date ASC, resultPriority ASC, game.id ASC)` with `W=0, D=1, L=2` so wins inside a same-kickoff batch land FIRST and longest captures the batch peak (the load-bearing user-spec invariant: "highest ever streak will be recorded including the games they won concurrently, even if one match ends before the other"). `longest` is MONOTONIC — never shrinks on a recompute (`save = max(prev.longest, computed.longest)`); a retroactive result correction that trims the actual run keeps the previously-stamped peak. Result corrections (`X → Y`, `X → null`, `null → X`) all handled by the same recompute — no reversal logic needed. Milestone dedup via `users.lastMilestoneFired`: thresholds [5, 10, 15, 20, 30, 50] (rescaled from the old daily 7/14/30/60/100 — wins-in-a-row is dramatically harder than calendar days); on each recompute fire the LARGEST milestone in `eligible = {M: M ≤ newCurrent AND M > prevStamp}`; on a current-drop below the stamp, drop the stamp to `max(M ≤ newCurrent)` so future re-crossings re-fire. Streakmaster badge is now TIERED (I/II/III at 5/10/15) mirroring the Recruiter ladder. **Cost**: O(N) per affected user where N = scored picks; sub-ms at our scale, full PL matchday fanout is trivial. **Don't switch back to a calendar-day model** — the rework was deliberate (pre-rework: lining up a month of picks in one day was a +1 increment, making streaks weak). **Don't add a freeze mechanism back** — there's no calendar boundary to freeze against; streaks now reset on individual L's. **Don't reintroduce a hook from PickService** — the result-scoring boundary is where streak state changes. Operator backfill via [scripts/recompute-streaks.mjs](scripts/recompute-streaks.mjs) after migration deploy (idempotent).
- **Recruiter referrer fan-out (Tier 30 Phase 3 A2)**: [services/BadgeService.js](services/BadgeService.js) `evaluateBadges` chains to the user's referrer when the user has any scored pick + a `referredByUserId`. - **Migrations framework (Tier 5.1)**: **never** add raw DDL to `runMigrations()` — it's a thin umzug shim. Add a new file under [migrations/](migrations/) via `npx sequelize-cli migration:generate --name foo` and use `IF NOT EXISTS` guards. `migrations/` and `seeders/` are versioned source code — always commit them. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md). **The `IF NOT EXISTS` guard is load-bearing for CI** (PR #18, 2026-05-28): the `DB migrations smoke` CI job runs `sequelize.sync({alter: false})` BEFORE `db:migrate` to mirror the dev/test boot order from [models/index.js](models/index.js).
